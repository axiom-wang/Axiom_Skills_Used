# Phase 2: 生成 SKILL 文件

## 目标

根据 Phase 1 的分析结果，生成完整的 SKILL 目录。

## 前置条件

Phase 1 的五份文档已就绪（技术栈报告、产品定义、架构约束、逐文件定制化标注、可定制点清单）。

## 执行步骤

### 2.1 生成 SKILL.md

入口文件，带 YAML frontmatter：

```yaml
---
name: <template-name>-generator
description: <一段推送式描述，涵盖触发短语>
---
```

正文包含：
- 概述（一句话 + "定向修改，不是从头重写"声明）
- 参数表（根据业务类型从 `rules/output-spec/skill-md.md` 的参数设计指引中推导）
- 执行流程（Phase A 分析 → Phase B 修改 → Phase C 检查 + verify）
- 模版声明（使用 `frontend` scene 模版，骨架文件已存在无需创建）
- reference/ 使用方式（分析分层 → 输出定制清单 → 定向修改）
- 目录结构（只列业务文件，骨架文件标注"已存在"）
- 注意事项 + 禁令

**description 写法要点**：
- 覆盖用户可能的触发短语（"帮我做个 XX 网站"、"生成一个 XX 风格的..."）
- 说明做什么 + 什么时候用
- 稍微"推送"一点，确保能被触发

### 2.2 生成 tasks/01-generate-code.md

**这是最重要的文件**，决定下游 AI 的输出质量。

**信息来源**：Phase 1 的架构约束（代码分层）+ 逐文件定制化标注（已写入 reference/STRUCTURE_MAP.md）。

**生成要点**：

1. 开头声明骨架文件已存在，无需创建
2. 核心方法论：按 STRUCTURE_MAP.md 标注执行定向修改（🎨 = 可改，未标注 = 保留）
3. 包含三阶段工作流（读标注 → 定向修改 → 完整性检查）
4. 包含代码分层模型（从当前模版实际情况定义 Layer 0-5 各层内容）
5. 包含修改规则和禁令
6. 包含完整性检查清单
7. 不包含场景化映射表——target 值由下游 AI 在 Phase A 结合用户需求得出

**详细内容规范见 `rules/output-spec/tasks.md`。**

### 2.3 生成 tasks/02-verify.md

内容：
- lint 命令 + 常见错误修复指引
- build 命令 + 构建失败排查
- UI 验证要点（根据业务类型定制）
- 最多 3 次重试，每次定位根本原因而非盲改
- 完成后回复用户的内容要点

### 2.4 构建 reference/

**信息来源**：Phase 1 的技术栈报告（文件分类）+ 产品定义 + 逐文件定制化标注。

**核心定位**：reference/ 是下游 AI 执行定向修改的代码基底。下游 AI 在这些源码文件上按 STRUCTURE_MAP.md 的标注做精确替换，因此所有业务文件必须完整保留，不可精简。

**完整性原则**：所有业务文件（Phase 1 §1.2 识别的）必须完整复制到 reference/，不做任何裁剪。原因：下游 AI 的工作方式是在原始源码上做定向修改（替换 🎨 标记的部分），如果源码不完整，就无法执行精确的行级替换。

**必须包含的文件**：
- **STRUCTURE_MAP.md** — 逐文件定制化标注，来自 Phase 1 §1.5 的产出
- **所有业务文件**（完整源码，保持子目录结构）：
  - pages/*（业务页面）
  - components/*（非 ui/ 的业务组件）
  - data/* / store/* / context/*（数据和状态）
  - hooks/*（自定义 hooks）
  - CSS 变量定义（index.css 中的 :root 部分）
  - App.tsx（布局骨架）
  - 路由配置相关代码

**执行步骤**：

1. 将 Phase 1 §1.5 的逐文件标注写入 `reference/STRUCTURE_MAP.md`
2. 将所有业务文件完整复制到 reference/（保持子目录结构）
3. 生成 CONTEXT.md：
   - 功能清单表
   - 页面导航关系（哪些页面之间有跳转，触发条件是什么）
   - 视觉风格描述 + 关键数值
   - 核心数据类型定义
   - 用户画像

### 2.5 生成 rules/

**architecture.md**：
- **布局骨架代码（必须严格遵守）**：从 reference/ 提取 App 层的实际 JSX 结构和关键 Tailwind 类名，以代码块展示，附 ASCII 拓扑图。声明为"合约"而非"建议"。
- **各布局区块规范**：分别说明主要布局组件的内部结构和关键类名
- **页面内容区通用模式**：说明页面内部内容的排列规律（如卡片网格、图表区、表格区的通用样式）
- 路由结构表
- Provider 层级
- 核心数据类型定义
- **组件职责表**（名称 / 职责 / 关键 Props）：
  - 职责描述必须精确到渲染形式（"水平条形图"而非"分析图表"，"进度条列表"而非"排名洞察"）
  - 复合组件（如首页）须列出其内部区块组成
  - 避免模糊词汇："洞察"、"概览"、"分析"→ 改为具体渲染形式
- 模版内置骨架文件列表（直接沿用，无需创建）
- 可定制点清单（来自 Phase 1 的可定制点分析，格式见 `rules/output-spec/rules.md`）
- **不可定制（固定骨架）声明**：明确列出不可改变的结构元素

**design-system.md**（合并原 coding-standards + design-system）：
- 编码规范摘要（组件格式、import 顺序、样式规则、lint 要求）
- **定制分析方法论**（教下游 AI 如何自主识别 reference/ 中的可修改项）：
  - 颜色分析方法：如何区分主色/强调色（可替换）vs 语义色/中性色（不替换）
  - 内容分析方法：如何识别品牌标识/导航文字/数据标签等可替换字符串
  - 数据结构分析方法：如何从 Context/Store 中提取可替换的实体定义/枚举值/指标
- **结构保真原则**：明确哪些代码类型视为结构（不可修改），包括 HTML 嵌套、CSS 非颜色类、组件区块划分、交互模式、数据流向
- 推断规则（当用户未指定时如何推断，优先级：用户显式声明 > 业务领域常识 > 保持与 reference 一致）
- AI 自主决策总原则（内部一致性 > 合理性 > 可用性 > 创造性）

**关键：不包含场景化映射表**（如"品牌关键词→配色"、"业务类型→数据结构"）。具体映射由下游 AI 在 Phase A 分析 reference/ 源码时自动得出。design-system.md 只教方法论和原则。

### 2.6 生成 prompt-template.md

给用户在 atoms.dev 直接复制使用的提示词模版，带 `{{变量}}` 插值语法。

**生成流程**：

1. **从 SKILL.md 参数表提取变量**：必填参数 → 必填变量，选填参数 → 可选变量或写入"变体提示"
2. **从产品定义提炼业务描述**：功能清单、页面结构、用户体验目标——用口语化的方式描述"这个网站要做什么"
3. **从 design-system.md 提取风格维度**：把设计规则转化为用户能理解的风格描述词（如"现代感"、"温暖亲切"、"高端奢华"）
4. **写使用说明**：面向非技术用户，解释变量含义和替换方法

格式和语气规范详见 `rules/output-spec/prompts.md`。

### 2.7 生成 prompts/ 即用型提示词

基于 prompt-template.md，生成 3 个已填充变量的完整提示词文案，用户可以直接复制到 atoms.dev 使用。

**选题原则**：

1. **prompt-1.md** — 最贴近原模版风格的典型案例（让用户快速理解"这个模版能做什么"）
2. **prompt-2.md** — 风格/行业明显不同的变体（展示模版的弹性）
3. **prompt-3.md** — 偏极端或创意方向的变体（展示模版的上限）

3 个提示词之间的差异应体现在：品牌调性、风格方向、目标用户、功能侧重等维度。

格式、语气和质量规范详见 `rules/output-spec/prompts.md`。

完整的 SKILL 目录，所有文件已写入 output_path。
